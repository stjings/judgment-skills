# Delegate Task

작업 하나를 맡기는 스킬이다. mattpocock의 `/implement`가 "스펙이나 티켓대로 만든다"에서 시작한다면, 이 스킬은 그 앞에 **경계 게이트**를 세우고, 끝에 **증거 게이트**로 넘긴다.

먼저 Skill 도구로 `judgment-gates`를 호출해 규칙을 읽는다. 호출할 수 없는 환경이면 이 문서만으로 진행한다.

## 1. 맥락을 모은다

- 사용자가 인자로 준 작업 설명, 티켓 번호, 스펙 경로를 읽는다. 티켓 참조가 있으면 이슈 트래커에서 본문과 댓글까지 가져온다(`docs/agents/issue-tracker.md`가 있으면 그 방법대로).
- 저장소가 있으면 `docs/intent.md`, `docs/agents/delegation.md`, 관련 ADR, `GLOSSARY.md`를 읽는다. 관련 코드도 직접 살펴 현재 동작을 파악한다.
- 의도 문서가 없고 작업이 목표나 정책을 건드리는 크기라면, 진행 전에 `/intent-grill`을 먼저 돌릴지 묻는다. 작은 수정이면 묻지 않고 진행한다.

## 2. 작업 브리프를 만든다

아래 브리프 초안을 채운다. 사용자가 준 내용은 그대로 쓰고, 에이전트가 추정한 칸에는 `(제안)`을 붙인다.

```md
# Task: <작업명>

- 목적과 대상 사용자: <왜 필요한가>
- 이번 범위: <포함할 것>
- 제외 범위: <하지 않을 것. 최소 1개>
- 경계표 위치: <judgment-gates 경계표의 어느 행인가. 예: 출석체크·포인트·쿠폰>

## 완료 기준
- [ ] <관찰 가능한 문장. 행위자, 조건, 관찰 결과>
- [ ] <실패 경로 최소 1개 포함>

## 검증 방법
| 완료 기준 | 검증 방법 | 실행 환경 |
|---|---|---|
| 기준 1 | <테스트 / 재현 시나리오 / 화면 확인 / 코드 검토> | <로컬 / 개발 / 스테이징> |

## 사람이 결정할 미정 사항
- <목표·정책·되돌리기 어려운 결정 중 아직 정해지지 않은 것>
```

완료 기준이 "잘 된다", "정상 동작한다"처럼 모호하면 관찰 가능한 문장으로 다시 써서 제안한다.

## 3. 충돌을 확인하고 합의한다

브리프를 의도 문서, ADR, 경계표와 대조한다.

- **충돌이 없으면** 브리프를 보여 주고 확인을 받는다.
- **충돌이 있으면** 그 부분만 멈추고 `judgment-gates`의 세 가지 선택으로 묻는다: 충돌 이유, 선택지, 장단점, 추천과 근거. 충돌과 무관한 부분은 합의되는 대로 진행해도 된다고 함께 알린다.
- **사람이 결정할 미정 사항**은 한 라운드에 번호를 붙여 묻고, 각 질문에 추천 답을 단다.

합의가 끝나면 저장소에 `docs/tasks/<작업명>.md`로 브리프를 저장한다. 이슈 트래커를 쓰는 프로젝트라면 이슈 본문에 같은 내용을 쓰는 쪽을 제안한다.

## 4. 경계 안에서 구현한다

- 합의된 범위의 되돌리기 쉬운 선택은 묻지 않고 진행한다.
- 의미 있는 가정과 설계 선택은 진행하면서 **결정 로그**에 한 줄씩 남긴다(무엇을, 왜, 대안). 되돌리기 어렵고 이유가 필요한 결정이면 ADR 후보로 표시한다.
- 구현 중 목표나 정책을 바꿔야 하는 상황이 생기면 그 부분을 멈추고 3번처럼 묻는다. 다른 부분은 계속한다.
- 테스트할 수 있는 동작이면 Skill 도구로 `tdd`를 호출해 합의한 검증 방법을 테스트로 먼저 고정한다(mattpocock skills가 없으면 같은 원칙으로 직접 진행: 실패하는 테스트 먼저, 한 번에 한 조각). 테스트할 지점(seam)은 시작 전에 사용자에게 확인한다.
- 타입체크와 관련 테스트를 자주 돌리고, 전체 테스트는 끝에 한 번 돌린다.
- 운영 배포, 실제 발송, 운영 DB 쓰기, 원격 push, 삭제는 사용자가 명시적으로 지시하기 전에는 실행하지 않는다. 대신 실행할 명령과 복구 절차를 준비해 둔다.

## 5. 증거와 함께 보고한다

구현이 끝나면 Skill 도구로 `evidence-review`를 호출하지 않는다(사용자 호출 전용이다). 대신 아래 형식으로 보고하고, 깊은 검토가 필요하면 사용자에게 `/evidence-review`를 권한다.

```md
## 완료 보고: <작업명>

### 기준별 결과
| 완료 기준 | 실행한 검증 (환경) | 관찰 결과 / 증거 위치 | 판정 |
|---|---|---|---|
| ... | ... | ... | 통과 / 실패 / 미검증 |

### 변경 내용과 이유
- <바뀐 사용자 동작과 시스템 동작>

### 결정 로그
- <가정·선택, 이유, 대안>

### 검증 한계
- <실행하지 못했거나 증거가 없는 항목과 이유>

### 남은 결정
- <현재 근거로 배포 가능한가, 추가 확인이 필요한가. 판단은 사람에게 넘긴다>
```

판정이 "미검증"인 항목을 "통과"로 바꿔 쓰지 않는다. 예상 결과를 실행 결과처럼 쓰지 않는다.

mattpocock skills의 `code-review` 스킬을 쓸 수 있고 git 저장소라면, 보고 전에 Skill 도구로 `code-review`를 호출해 Standards/Spec 두 축 검토를 돌리고 결과를 보고에 붙인다. 이때 Spec은 2번에서 합의한 브리프다.
