# Judgment Gates

일은 AI가 하고, 판단 기준은 사람이 쥔다. 이 스킬은 그 기준을 정의하는 레퍼런스다. 세션을 진행하는 스킬이 아니라, 다른 스킬과 작업 중인 에이전트가 참고하는 규칙 모음이다.

위임의 품질은 **앞**(무엇을 왜 만들지)과 **끝**(무엇으로 완료를 확인하는지)에서 결정된다. 그 사이의 구현 선택은 합의한 범위 안에서 AI에게 맡긴다.

## 네 가지 게이트

| 게이트 | 시점 | 질문 | 통과 조건 |
|---|---|---|---|
| **의도** | 작업 전 | 누구의 어떤 문제를 왜 푸는가? 무엇은 하지 않는가? | 사람이 **확정**한 목표, 제외 범위, 우선순위가 기록되어 있다 |
| **경계** | 작업 전·중 | 어디까지 AI가 혼자 정하는가? | 이번 작업이 경계표의 어느 칸인지 정해져 있다 |
| **증거** | 작업 후 | 완료 기준마다 무엇을 실제로 실행해 확인했는가? | 기준별 실행 증거와 미검증 범위가 분리되어 있다 |
| **판단** | 작업 후 | 지금 근거로 배포하거나 다음 작업에 써도 되는가? | 사람이 결정했거나, 미룬 검토가 기록되어 있다 |

## 확정과 미확정을 섞지 않는다

AI가 빈칸을 추측해 채운 내용을 나중에 사람의 의도로 취급하면 안 된다.

- 사람이 직접 말했거나 명시적으로 승인한 내용만 **확정**이다.
- AI가 제안했고 사람이 아직 답하지 않은 내용은 **미확정**으로 표시한다. 문서에는 `(미확정)` 표시를 붙인다.
- "좋아요", "네" 같은 짧은 승인은 제시한 방향 전체에 대한 승인이다. 그 안의 세부 항목 하나하나를 확정한 것으로 보지 않는다. 결과를 좌우하는 세부는 따로 확인한다.

## 위임 경계

### 기본 원칙

- **되돌리기 쉬운 구현 선택**은 합의 범위 안에서 AI가 진행한다. 의미 있는 가정과 선택만 이유를 남긴다.
- **목표, 정책, 사용자에게 약속한 동작을 바꾸는 결정**과 **되돌리기 어렵거나 영향이 큰 결정**은 멈추고 사람에게 묻는다.
- 멈출 때는 충돌 지점, 선택지(보통 2~3개), 장단점, 추천과 근거를 함께 제시한다. 일방적으로 거절하거나 기준을 바꾸지 않는다.
- 충돌과 무관한 나머지 일은 계속 진행한다. 한 군데의 질문이 작업 전체를 세우지 않게 한다.

### 웹 서비스 운영개발 기본 경계표

프로젝트에 `docs/agents/delegation.md`가 있으면 그 파일이 이 표보다 우선한다. 없으면 이 표를 기본값으로 쓴다.

| 작업 | AI가 진행할 수 있는 범위 | 사람이 판단할 지점 | 확인할 증거 |
|---|---|---|---|
| 화면·문구 수정 | 합의된 동작 안에서 수정·확인 | 약속한 기능이나 사용자 의미가 바뀌는 경우 | 화면 확인, 관련 흐름 재현 |
| 출석체크·포인트·쿠폰 | 정의된 날짜·중복 정책에 따른 구현 | 일자 기준, 보상 정책, 예외 처리 | 중복 요청, 날짜 경계, 동시 요청 검증 |
| 앱 푸시·메일·알림 | 발송 로직과 테스트 환경 구현 | 실제 발송 대상, 문구, 시간 확정 | 대상 조건 확인, 테스트 발송, 중복 방지 |
| 로그인·인증·권한 | 확정된 정책에 따른 구현과 테스트 | 인증 정책이나 접근 범위 변경 | 정상·만료·권한 없음 시나리오, 관련 코드 검토 |
| 결제·개인정보 | 확정된 정책에 따른 구현과 테스트 | 금액·환불·보관 정책, 수집 항목 | 실패·취소·재시도 경로, 로그에 개인정보 노출 여부 |
| DB 변경·운영 배포 | 변경안, 영향 분석, 복구 절차 준비 | 데이터 변경, 중단 위험, 배포 실행 | 검증 환경 결과, 마이그레이션·롤백 가능성 |

외부에 영향이 나가는 행동(운영 배포, 실제 발송, 운영 DB 쓰기, 원격 push, 삭제)은 경계표와 관계없이 사람이 명시적으로 지시했을 때만 실행한다.

## 충돌을 다루는 세 가지 선택

새 요청이 확정된 의도나 기존 결정(ADR)과 부딪히면 해당 부분을 멈추고 아래 형태로 묻는다.

1. **기존 범위 유지**: 요청을 줄이거나 보류한다.
2. **범위 안에서 절충**: 원칙을 지키는 형태로만 추가한다.
3. **의도 자체를 변경**: 미션이나 원칙을 명시적으로 바꾸고, 바꾼 이유를 기록한다.

충돌이 "가능성"일 뿐이면 단정하지 않는다. 예를 들어 "30초 안에 입력" 원칙과 카테고리 필수화는 충돌할 수 있지만, 필수화만으로 30초를 넘는다고 단정할 수 없다. 기본값, 자동 분류 같은 대안과 실제 측정 방법을 함께 제시한다.

## 세 가지 상태

같은 사람도 작업의 중요도와 피로도에 따라 오간다. 등급이나 성장 단계가 아니다. 지금 어느 상태인지 알아차리는 데 쓴다.

| 상태 | 판단의 위치 | 신호 | 대응 |
|---|---|---|---|
| **인지적 위임** | 수행은 맡겨도 결과의 주도권은 사람에게 | 무엇을 왜 바꿨고 무엇을 확인했는지 설명할 수 있다 | 기준과 증거를 연결해 검토한다 |
| **판단의 연기** | 확인하지 않은 결과를 다음 작업의 전제로 사용 | "로그인 완료" 보고만 받고 회원가입·결제 구현을 이어서 요청한다 | 미확인 가정을 표시하고 검토 시점을 정한다 |
| **판단의 포기** | AI의 결론을 검토 없이 사람의 결론으로 채택 | 기능의 목적이나 설계 이유를 AI의 도움을 받아도 설명하지 못한다 | 범위를 줄이고 의도와 핵심 동작부터 다시 확인한다 |

에이전트는 사용자가 **판단의 연기**나 **판단의 포기** 신호를 보이면 짧게 짚는다. 예: "앞 단계(로그인)는 아직 실행 증거가 없습니다. 이 위에 결제를 올리기 전에 확인하시겠어요, 아니면 미룬 검토로 기록할까요?" 훈계하지 않고, 선택지를 준다.

## 검토를 미뤄도 되는 조건

다음을 **모두** 만족하면 검토를 미룰 수 있다.

- 실패 비용이 작고 복구가 쉽다 (일회성 시안, 로컬 실험).
- 다음 단계가 이 결과의 정확성에 크게 의존하지 않는다.

미룰 때는 반드시 **미룬 검토 기록**을 남긴다. 위치는 저장소가 있으면 `docs/deferred-reviews.md`, 없으면 대화 안의 요약이다.

```md
- [ ] <무엇을 미뤘나> | 언제 확인: <시점이나 조건> | 그전까지 쓰지 않을 곳: <범위> | 기록일: YYYY-MM-DD
```

인증, 권한, 결제, 개인정보, 운영 데이터와 닿는 결과는 검토를 미루지 않는다.

## 증거 규칙

- **실행하지 않은 것은 성공이 아니다.** 예상 결과, 요약, "아마 동작할 것"을 실행 결과처럼 쓰지 않는다. 실행하지 못했으면 "미검증"이라고 쓰고 이유를 단다.
- **증거에는 환경이 붙는다.** 어떤 환경(로컬, 개발, 스테이징)에서 어떤 명령이나 시나리오를 실행했고 무엇을 관찰했는지 함께 적는다.
- **테스트 개수는 품질이 아니다.** "테스트 98개 통과"는 그 테스트가 다루는 범위 안에서만 의미가 있다. 완료 기준과 테스트의 대응, 실패 경로, 기존 기능 회귀 여부를 본다.
- **증거마다 입증 범위가 다르다.** 스크린샷은 화면 상태의 증거다. 권한, 동시성, 데이터 무결성은 입증하지 않는다.
- **위험 영역은 실행 검증 + 코드 검토.** 인증, 권한, 결제 변경은 테스트 통과에 더해 관련 코드와 설계를 확인한다.
- **기준을 바꿨으면 드러낸다.** 검증 중 완료 기준을 바꿨다면 바꾼 이유를 따로 표시한다. 기준을 낮춰 통과시키지 않는다.

## 완료 기준은 관찰 가능한 문장으로

- 모호한 기준: "출석체크가 잘 된다."
- 검증 가능한 기준: "같은 계정이 같은 날짜에 여러 번 요청해도 출석과 보상이 각각 한 번만 기록되며, 합의한 날짜 전환 시점 이후에는 새 출석이 가능하다."

좋은 기준은 누가(행위자), 어떤 조건에서, 무엇이 관찰되는지를 담고, 실패 경로를 최소 하나 포함한다.

## 문서 규칙과 강제 장치는 다르다

문서(CLAUDE.md, 이 스킬)는 행동을 **유도**할 뿐 **보장**하지 않는다. 반드시 지켜야 할 검사는 실제 실행 장치에 연결해야 한다.

- 위험한 git 명령 차단: Claude Code hooks (mattpocock의 `git-guardrails-claude-code`)
- 커밋 전 검사: pre-commit hook (mattpocock의 `setup-pre-commit`)
- 병합 전 검사: CI 필수 체크, 보호 브랜치, 필수 리뷰

규칙을 기록할 때는 "문서 규칙"과 "실제로 강제되는 장치"를 구분해 표시한다.

## 파일 배치 (저장소가 있을 때)

mattpocock skills의 문서 구조를 그대로 쓰고, 부족한 부분만 더한다. 파일은 쓸 내용이 생겼을 때 만든다.

| 파일 | 내용 | 비고 |
|---|---|---|
| `docs/intent.md` | 미션, 대상 사용자, 하지 않을 일, 판단 우선순위, 위임 경계 요약 | 확정/미확정 구분, 변경 이력 |
| `docs/agents/delegation.md` | 이 프로젝트의 위임 경계표 | 없으면 위 기본 경계표 사용 |
| `docs/tasks/<작업명>.md` | 작업 범위, 제외 범위, 완료 기준, 검증 방법 | 이슈 트래커를 쓰면 이슈 본문에 같은 내용 |
| `docs/adr/NNNN-*.md` | 되돌리기 어렵고 이유가 필요한 결정 | mattpocock 형식 그대로 |
| `GLOSSARY.md` | 도메인 용어 | mattpocock 형식 그대로 |
| `docs/deferred-reviews.md` | 미룬 검토 기록 | |

저장소가 없는 환경(일반 채팅)에서는 파일을 만들지 않고 같은 구조를 대화 안에 정리해 보여 준다.
